# FF5 补丁三个 sysfs 节点解读

| 节点 | 一句话 | 比喻 |
|---|---|---|
| `ff5_update_status` | 现在 ADSP 什么状态？ | 汽车的仪表盘（速度/油量/档位） |
| `ff5_update_gate_probe` | 我那个"禁止操作"的闸门到底灵不灵？ | 按一下试喇叭响不响 |
| `ff5_update_votes` | 谁借了 ADSP、还了没有？ | 图书馆的借还账本 |

---

## 第一部分：节点输出解读 —— 用户视角"cat 出来的是什么"

### 一、ff5_update_status —— 仪表盘

你实际看到的是：

```
  patch=FF5_RPROC_PROBE_01 state=2 power=1 gate=0 reload=0 fw=adsp.mdt
```

逐个字段：

| 字段 | 值 | 意思 | 用大白话 |
|---|---|---|---|
| patch | FF5_RPROC_PROBE_01 | 补丁版本标记 | "这是第 1 版补丁"（确认你刷的固件确实带这个补丁） |
| state | 2 | 状态机当前值 | 2 = RUNNING，ADSP 正在运行（见下方对照表） |
| power | 1 | 引用计数 | "现在有 1 个用户在用 ADSP"（不是电量！） |
| gate | 0 | 门控标记 | 0 = 门是开的（没人上锁，操作可以正常进行） |
| reload | 0 | 保留字段（硬编码） | 暂时没用，占位 |
| fw | adsp.mdt | 当前固件名 | ADSP 跑的是 adsp.mdt 这套固件 |

state 完整对照（0~6）：

```
  0 = OFFLINE    关机
  1 = SUSPENDED  挂起
  2 = RUNNING    运行中   ← 你看到的
  3 = CRASHED    崩溃了
  4 = DELETED    已删除
  5 = ATTACHED   别人启动的，我只接管
  6 = DETACHED   已分离
```

#### 举例：什么时候这个输出会变

场景 A（正常）：刚开机，没人用 ADSP

```
  state=0 power=0 gate=0 fw=adsp.mdt
```

→ ADSP 关着，没用户。

场景 B（有人在用）：sensor 驱动启动了 ADSP

```
  state=2 power=1 gate=0 fw=adsp.mdt
```

→ 运行中，1 个用户。

场景 C（要更新，上了闸门）：

```
  state=2 power=1 gate=1 fw=adsp.mdt
```

→ gate=1 表示门被锁上了，此刻任何人想 boot/shutdown/detach 都会被拒绝（返回 -EBUSY）。

场景 D（崩溃了）：

```
  state=3 power=1 gate=0 fw=adsp.mdt
```

→ state=3 = CRASHED，ADSP 挂了，等待恢复。

> 所以这个节点就是让你 cat 一下就知道"ADSP 现在到底活着没、有几个人在用、门锁没锁"。

### 二、ff5_update_gate_probe —— 试喇叭

你实际看到的是：

```
  before=0 held=-16 after=0 pass=1 hardware_ops=0
```

它做的事，用大白话讲：

> 我假装要锁门，看看锁到底管不管用，然后立刻把门打开。全程不动任何真实设备。

分三步（对应输出）：

| 字段 | 值 | 意思 |
|---|---|---|
| before | 0 | 锁之前先试一下：门能开吗？→ 0 = 能（放行） |
| held | -16 | 锁上之后再试：门能开吗？→ -16 就是 -EBUSY = 不能开（被拒绝）✅ |
| after | 0 | 解锁之后再试：→ 0 = 又恢复能开了 ✅ |
| pass | 1 | 上面三步都符合预期 → 自检通过 |
| hardware_ops | 0 | 没有做任何硬件操作（没真的开关 ADSP） |

#### 用数字演一遍（就像代码里做的）

```
  ① 一开始门是开的：       before = admit() = 0        （放行）
  ② 我插一个"占用"标记：   （相当于挂上"正在使用"的牌子）
  ③ 再试：                 held  = admit() = -16       （-EBUSY，被挡住 ✅）
  ④ 摘掉标记：
  ⑤ 再试：                 after = admit() = 0         （又放行 ✅）
  ⑥ 全对 → pass=1
```

为什么要做这个自检？ 因为如果将来真正做"在线更新"，更新期间就得靠这道闸门挡住别人。你得先证明"闸门真的能挡住"，否则等真更新时才发现闸门是坏的，ADSP 就被别人抢着 shutdown 了，后果严重。

失败长什么样？ 假如 held 不是 -16（比如也是 0），说明闸门没生效：

```
  before=0 held=0 after=0 pass=0 hardware_ops=0
```

→ pass=0，你就知道"门控机制坏了，不能做在线更新"。

> 注意：它只证明"闸门本身在同一把锁下有效"，不证明"真的并发时别人一定被挡住"（那需要真并发压测）。所以补丁说明里特意写了这个边界。

### 三、ff5_update_votes —— 借还账本（patch 02）

这个稍微复杂，但比喻最好懂：ADSP 像一本图书馆的书，这个账本记录"谁借了、还了、现在欠几本"。

输出长这样（我编一组数据）：

```
  patch=FF5_RPROC_VOTES_02 power=1 net=1 balanced=1 objrefs=0 dropped=0
  total op=boot ok=3 fail=0
  total op=shutdown ok=2 fail=0
  total op=detach ok=0 fail=0
  total op=get ok=5 fail=0
  total op=put ok=5 fail=0
  site op=boot ok=2 fail=0 last_err=0 caller=sensor_driver+0x1a4
  site op=boot ok=1 fail=0 last_err=0 caller=audio_driver+0x2f0
  site op=shutdown ok=2 fail=0 last_err=0 caller=sensor_driver+0x220
```

#### 第一行：总账

| 字段 | 值 | 意思 |
|---|---|---|
| power | 1 | 现在引用计数 = 1（还有 1 个用户） |
| net | 1 | 净启动次数 = boot次数 - shutdown次数 - detach次数 = 3 - 2 - 0 = 1 |
| balanced | 1 | net == power 吗？1 == 1 → 平衡 ✅ |
| objrefs | 0 | 对象引用净数 = get次数 - put次数 = 5 - 5 = 0 → 没有泄漏 ✅ |
| dropped | 0 | 有几次记录因为表满了被丢弃（0 = 没丢） |

#### 为什么 net 要减 detach？

因为 power 的规则是：

- boot → power +1
- shutdown → power -1
- detach → power -1
- attach → power +1（但这个补丁没统计 attach，简化了）

所以"净启动次数" = boot - shutdown - detach，应该等于当前的 power。

#### balanced=1 意味着什么？（重点）

balanced=1 = "每次启动都有对应的关闭/分离，账实相符"。

- 如果 balanced=1 → 你可以安全地把 power 降到 0（把最后一个用户也关掉）→ 才能做在线更新。
- 如果 balanced=0（比如 power=1 但 net=2）→ 账本和实际对不上，说明有"启动了但没人负责关"的情况，这时候贸然更新会出问题。

#### objrefs 是什么？

`rproc_get_by_phandle()` / `rproc_put()` 是"拿到一个 ADSP 对象引用 / 还回去"。如果 get 了没 put，对象就泄漏，即使 power 归零也没法删除/换固件。objrefs=0 表示没有泄漏。

#### site ... caller=xxx 是什么？（最有用）

它告诉你是哪个驱动、在哪一行代码发起的操作：

```
  site op=boot     ok=2 caller=sensor_driver+0x1a4    ← sensor 驱动启动了 2 次
  site op=boot     ok=1 caller=audio_driver+0x2f0     ← audio 驱动启动了 1 次
  site op=shutdown ok=2 caller=sensor_driver+0x220    ← sensor 驱动关闭了 2 次
```

用途：将来你发现"ADSP 关不掉（power 降不到 0）"，一查这个账本就立刻知道——是 audio_driver 借了没还（boot 了 1 次但没 shutdown）。直接定位到具体驱动和代码地址，不用瞎猜。

### 四、把三个节点串起来看一个完整故事

假设你想在线更新 ADSP，你会这样用：

```bash
  # 1. 先看现在什么状态
  cat .../ff5_update_status
  # state=2 power=1 gate=0 fw=adsp.mdt     → 运行中，1 个用户

  # 2. 查账本，看是谁在用、账平不平
  cat .../ff5_update_votes
  # power=1 net=1 balanced=1 objrefs=0
  # site op=boot ok=1 caller=sensor_driver+0x1a4
  # → 是 sensor 驱动在用；账是平的（能对上）

  # 3. 试一下闸门灵不灵
  cat .../ff5_update_gate_probe
  # pass=1  → 闸门有效，将来可以靠它独占
```

结论：现在 sensor 在用（power=1），你需要让 sensor 先释放（power 降到 0），然后才能 shutdown ADSP 换固件。而 balanced=1、objrefs=0、pass=1 说明"账目干净、闸门可用"，具备做在线更新的基础条件。

---

### 五、一张图总结

```
  ff5_update_status    → "现在怎么样"      state/power/gate/fw      （仪表盘）
  ff5_update_gate_probe→ "闸门灵不灵"      before/held/after/pass   （试喇叭）
  ff5_update_votes     → "谁借谁还、平不平" power/net/balanced/...   （账本）
```

- state=2 = 运行中
- power=1 = 1 个用户
- gate=0 = 门没锁
- balanced=1 = 账实相符
- objrefs=0 = 没泄漏
- pass=1 = 闸门有效

看到这些值都"正常"，就说明：ADSP 状态清楚、引用计数干净、独占闸门可用——在线更新固件的地基是牢的。

## 第二部分：代码机制 —— 是"注册"，不是"调用"

### 一、先看代码里到底做了什么（是"注册"，不是"调用"）

#### 第 1 步：把 `_show` 函数指针塞进一个结构体

```c
  static struct device_attribute dev_attr_ff5_update_status =
      __ATTR(ff5_update_status, 0400, ff5_update_status_show, NULL);
```

这行 `__ATTR(...)` 是个宏，展开后大致等于：

```c
  struct device_attribute dev_attr_ff5_update_status = {
      .attr = { .name = "ff5_update_status", .mode = 0400 },   // 文件名 + 权限
      .show  = ff5_update_status_show,   // ← 函数指针存这里！
      .store = NULL,
  };
```

关键：`ff5_update_status_show` 这个名字只在这里出现一次，作为函数指针存进了结构体。所以你在代码里 grep `"ff5_update_status_show("` 只会找到它的定义，找不到"调用"——因为调用是通过指针发生的。

#### 第 2 步：把结构体放进"属性数组"

```c
  static struct attribute *ff5_probe_attrs[] = {
      &dev_attr_ff5_update_status.attr,
      &dev_attr_ff5_update_gate_probe.attr,
      &dev_attr_ff5_update_votes.attr,
      NULL,
  };

  static const struct attribute_group ff5_probe_group = {
      .attrs = ff5_probe_attrs,
  };
```

#### 第 3 步：在 `rproc_add()` 时把这一组属性注册给 sysfs

```c
  // remoteproc_core.c: rproc_add()
  ret = rproc_ff5_probe_add(rproc);   // ← 注册的入口

  // remoteproc_ff5_probe.c
  int rproc_ff5_probe_add(struct rproc *rproc)
  {
      ...
      ret = sysfs_create_group(&rproc->dev.kobj, &ff5_probe_group);  // ★ 注册到 sysfs
      ...
  }
```

`sysfs_create_group(&rproc->dev.kobj, ...)` 就是告诉内核：

> "在 remoteprocN 这个设备目录下，创建 ff5_update_status 等文件；用户读它时，去调用我登记的那个 show 函数。"

于是内核里就出现了：

```
  /sys/class/remoteproc/remoteprocN/ff5_update_status       （mode 0400）
  /sys/class/remoteproc/remoteprocN/ff5_update_gate_probe
  /sys/class/remoteproc/remoteprocN/ff5_update_votes
```

---

### 二、你 cat 的时候，内核怎么"回调"到 `_show`

真正的"调用"发生在你敲 `cat` 的那一刻，链路是这样的：

```
  用户态：cat /sys/class/remoteproc/remoteproc0/ff5_update_status
     │
     ▼
  VFS：vfs_read()
     │
     ▼
  sysfs 文件系统：kernfs 找到这个文件对应的 kobject + attribute
     │
     ▼
  fs/sysfs/file.c: sysfs_kf_read() → sysfs_kf_seq_show()
     │
     ▼
  drivers/base/core.c: dev_attr_show()
          if (attribute->show)
              return attribute->show(dev, attribute, buf);   // ★ 通过函数指针回调
     │
     ▼
  你的代码：ff5_update_status_show(dev, attr, buf)   ← 这里才真正执行
     │
     ▼
  它 sysfs_emit(buf, "patch=... state=... power=...") 把字符串写进 buf
     │
     ▼
  内核把 buf 里的内容返回给 cat，cat 打印到屏幕
```

所以"调用者"是内核的 sysfs 框架，不是你的驱动代码。你的代码只负责"注册一个回调"，剩下的交给内核。

---

### 三、用一个类比

想象你在一家餐厅：

1. **注册**：你把"我的招牌菜是宫保鸡丁"写进菜单，交给前台（`sysfs_create_group`）。
2. **客人点单**：客人说"来一份宫保鸡丁"（`cat ff5_update_status`）。
3. **前台通知厨房**：前台按菜单找到你的档口，喊你"做一份宫保鸡丁"（内核通过函数指针回调 `ff5_update_status_show`）。
4. **你做菜**：你炒好端出去（`sysfs_emit` 写 buf）。

你在后厨的代码里不会写"客人来了"这个逻辑——你只登记了"这个菜归我做"，客人点单时自然是前台（内核）来叫你。

---

### 四、为什么"grep 不到调用"

- `ff5_update_status_show` 的定义在 `remoteproc_ff5_probe.c` 里。
- 它的地址被 `__ATTR` 存进 `dev_attr_ff5_update_status.show`。
- 真正的调用在内核的 `dev_attr_show()` 里，通过 `attribute->show(...)` 发生——不在你的代码里。

如果你想"看到"这个调用，可以在内核源码里看这两个文件：

```
  fs/sysfs/file.c        → sysfs_kf_read / sysfs_kf_seq_show
  drivers/base/core.c    → dev_attr_show()
```

`dev_attr_show()` 里那句 `attribute->show(dev, attribute, buf)` 就是"调用你的函数"的地方。

---

### 五、`gate_probe` / `votes` 完全一样

三个节点的机制完全相同，只是注册了不同的回调：

```c
  __ATTR(ff5_update_status,     0400, ff5_update_status_show,      NULL)
  __ATTR(ff5_update_gate_probe, 0400, ff5_update_gate_probe_show,  NULL)
  __ATTR(ff5_update_votes,      0400, ff5_update_votes_show,       NULL)
```

所以：

- 你 `cat ff5_update_status` → 内核调 `ff5_update_status_show`
- 你 `cat ff5_update_gate_probe` → 内核调 `ff5_update_gate_probe_show`
- 你 `cat ff5_update_votes` → 内核调 `ff5_update_votes_show`

注意 `0400` 是"只读"权限：只有 `show`（读），`store = NULL`（写）。所以这些节点你只能 `cat` 看，不能 `echo` 写——这也符合补丁说的"只读诊断节点"。如果你尝试 `echo x > ff5_update_status`，会失败（因为没有 `store` 回调）。

---

### 六、还有一点：`store` 为 `NULL` 时写会怎样

```c
  if (attribute->store)
      ret = attribute->store(dev, attribute, buf, count);
  else
      return -EIO;   // 只读属性，写会返回错误
```

所以这三个节点是纯只读的，写不进去。

---

### 一句话总结

> 代码里做的是"注册回调"（`sysfs_create_group` + `__ATTR(..., show, ...)`），真正的"调用"是内核在你 `cat` 时通过函数指针 `attribute->show()` 完成的，所以你在驱动代码里 grep 不到调用点。

如果你想验证，可以在设备上 `cat` 之后 `dmesg` 或加打印，或者直接看 `sysfs_create_group` 的返回值——但最直观的就是：能 `cat` 出内容，就说明回调被调用了。

### patch 04：在会话里真正停启 ADSP（同固件）

> patch 03 给了你"门禁卡"（占住 ADSP）；patch 04 让你在占住之后，能真正"关灯再开灯"——把 ADSP 停掉再启动（同一份固件），而且全程不用重启 AP。

#### 一、它做了什么（一句话）

在会话 fd 上加了两个命令：

```
  exec 3<>/dev/ff5_adsp_update    # BEGIN（必须读写方式打开）
  echo stop  >&3                  # RUNNING → OFFLINE，power 1 → 0
  echo start >&3                  # OFFLINE → RUNNING，power 0 → 1
  exec 3<&-                       # END
```

- `stop`：只在 `RUNNING && power==1` 时执行 → 关掉 ADSP
- `start`：只在 `OFFLINE && power==0` 时执行 → 用当前固件重新启动
- 条件不满足 → 返回 `-EINVAL`
- 不替换固件，只是"同固件停启"

#### 二、核心机制：借票 / 还票（最巧妙的地方）

回顾 patch 02：ADSP 只有 loader 的一张运行票（`power==1`，`vote_held=1`）。

这个补丁不改 loader，而是**"借用"它的票**：

```
  正常状态：  power=1（loader 的票）      ADSP RUNNING
                  │
     echo stop    │  ← 借走这张票
                  ▼
              power=0                      ADSP OFFLINE
                  │
     echo start   │  ← 把票还回去
                  ▼
              power=1（还是 loader 的票）  ADSP RUNNING
```

关键：loader 全程以为自己的票还在（`vote_held=1` 没变），所以 loader 一行代码都不用改。这就是为什么提交里说"借用 loader 那张票"。

#### 三、core 改动：gated + owner（让会话自己能过门控）

##### 问题

patch 03 的门控是"只要 xarray 里有 marker，就返回 `-EBUSY`"。但会话自己（持门控的人）需要能调用 `rproc_boot/shutdown`——总不能让会话自己也被拦住。

##### 解决：给 boot/shutdown 加个 owner 参数

```c
  // 原来的 rproc_boot() 拆成内部实现 + 两个入口
  static int rproc_boot_gated(struct rproc *rproc, const void *owner,
                              unsigned long caller)
  {
      ...
      ret = owner ? rproc_ff5_admit_owner_locked(rproc, owner)  // 会话：校验"门控是我持有的"
                  : rproc_ff5_admit_locked(rproc);              // 公共：门控有 marker 就拒
      ...
  }

  int rproc_boot(struct rproc *rproc)          // 公共入口
  {
      return rproc_boot_gated(rproc, NULL, _RET_IP_);   // owner=NULL
  }
  EXPORT_SYMBOL(rproc_boot);

  int rproc_ff5_boot_owned(struct rproc *rproc, const void *owner)  // 会话入口（不导出）
  {
      return rproc_boot_gated(rproc, owner, _RET_IP_);
  }
```

`rproc_shutdown` 同理拆成 `rproc_shutdown_gated` + `rproc_shutdown` + `rproc_ff5_shutdown_owned`。

##### 两个准入函数（在 ff5_probe.c）

```c
  // 公共入口用：门控里有任何 marker 就拒绝
  int rproc_ff5_admit_locked(struct rproc *rproc)
  {
      return xa_load(&ff5_probe_gates, rproc->index) ? -EBUSY : 0;
  }

  // 会话入口用：只有门控持有者 == owner 才放行（门控为空也拒）
  int rproc_ff5_admit_owner_locked(struct rproc *rproc, const void *owner)
  {
      return xa_load(&ff5_probe_gates, rproc->index) == owner ? 0 : -EBUSY;
  }
```

这就是"会话能过、别人不能过"的机制：

- 会话调用 `rproc_ff5_shutdown_owned(rproc, ud)` → `admit_owner_locked` 发现 xarray 里存的正是 `ud` → 放行 ✅
- 别人（loader/sysfs/cdev）调 `rproc_shutdown` → `admit_locked` 发现有 marker → 拒绝 ❌

#### 四、ff5_update_write() —— stop/start 命令的实现

```c
  static ssize_t ff5_update_write(struct file *file, const char __user *ubuf,
                                  size_t count, loff_t *ppos)
  {
      // 1. 解析 "stop" / "start"
      if (sysfs_streq(cmd, "stop"))       stop = true;
      else if (sysfs_streq(cmd, "start")) stop = false;
      else return -EINVAL;

      // 2. 串行化命令（与 remove 互斥）
      mutex_lock(&ud->op_lock);
      if (ud->removed) { ret = -ENODEV; goto out; }

      // 3. 先读当前状态（锁内读，锁外执行）
      mutex_lock_interruptible(&rproc->lock);
      state = rproc->state;
      power = atomic_read(&rproc->power);
      mutex_unlock(&rproc->lock);

      // 4. 检查条件后执行
      if (stop && state == RPROC_RUNNING && power == 1)
          ret = rproc_ff5_shutdown_owned(rproc, ud);      // ← 会话身份调用
      else if (!stop && state == RPROC_OFFLINE && power == 0)
          ret = rproc_ff5_boot_owned(rproc, ud);          // ← 会话身份调用
      else
          ret = -EINVAL;

  out:
      mutex_unlock(&ud->op_lock);
      dev_info(..., "ff5 update %s: state=%u power=%d ret=%d\n", ...);
      return ret ? ret : count;
  }
```

注意第 3、4 步之间释放了锁（"检查与执行的空档"）。为什么安全？因为门控挡住了所有人，只有"崩溃处理"可能在这期间把 `RUNNING` 改成 `CRASHED`——而 core 在 `rproc_shutdown_gated` 内部会重新加锁再检查 `state`，这时如果已经是 `CRASHED` 就返回 `-EINVAL`。

#### 五、锁与死锁（这段最烧脑，但很关键）

##### 死锁风险从哪来

停止 ADSP 会拆掉它下面的 GLINK/rpmsg 子设备，这些子驱动的 remove/probe 可能会注册/注销 misc 设备（需要 `misc_mtx`）。而 open 是在 `misc_open` 持有 `misc_mtx` 时被调用的。

```
  如果 open 阻塞等 rproc->lock，而 stop 持有 rproc->lock 又去等 misc_mtx
  → 经典 ABBA 死锁
```

##### 解决方案（三道防线）

1. **open 改成 trylock**（不再阻塞等 `rproc->lock`）：

```c
  - ret = mutex_lock_interruptible(&rproc->lock);
  + if (!mutex_trylock(&rproc->lock)) {   // 拿不到就返回 -EBUSY
  +     ret = -EBUSY;
  +     goto out;
  + }
```

行为变化：ADSP 正在启停时，open 会直接失败（返回 `-EBUSY`），而不是干等。

2. **stop/start 不持 `ff5_update_mutex`**（只持 `op_lock` + `rproc->lock`）：

```c
  mutex_lock(&ud->op_lock);      // 只持 op_lock
  ...
  ret = rproc_ff5_shutdown_owned(rproc, ud);   // 内部拿 rproc->lock
  ...
  mutex_unlock(&ud->op_lock);
```

3. **锁顺序单向**（提交里明确写了）：

```
  misc_mtx → ff5_update_mutex → rproc->lock
  op_lock  → ff5_update_mutex → rproc->lock
  无反方向获取
```

##### remove 的顺序也改了

```c
  misc_deregister(&ud->misc);      // 1. 先注销设备（没有新 open）
  mutex_lock(&ud->op_lock);        // 2. ★ 等进行中的 stop/start 命令执行完
  mutex_lock(&ff5_update_mutex);
  ud->removed = true;
  mutex_lock(&rproc->lock);
  ff5_update_gate_drop_locked(ud); // 3. 去掉门控
  ...
  mutex_unlock(&ud->op_lock);
```

第 2 步是这次新增的：先等正在执行的 stop/start 完成，再拆门控，避免"remove 和命令打架"。

#### 六、验收数据说明什么

| 测试 | 结果 | 说明 |
|---|---|---|
| 整体 | `boot_id` 全程不变，OEM 不变，固件始终 `adsp.mdt` | 没重启 AP，同固件 |
| loader SSR | `ssr_write=0`，offline → running，账本 2/1 | 原有 SSR 路径没被破坏 |

| 账本 | 依次 3/2、4/3、5/4，`balanced=1` | 借票/还票账目正确 |
| OFFLINE 结束会话 | `stop=0`，关 fd 后 offline/power0/gate0 | 可以故意让 ADSP 保持离线 |
| 新会话恢复 | `reopen=0`→`start=0`→running/power1/gate0 | 离线后能重新拉起 |

账本对账（提交里）：

```
  loader 原路径: boot=2, shutdown=1
  会话 write:    boot=4, shutdown=4
  合计:          boot=6, shutdown=5 → net=1 = power ✅ balanced=1
```

#### 七、一张图总结

```
                     用户态
                       │
       open("/dev/ff5_adsp_update")        ← BEGIN（持门控）
                       │
       ┌───────────────┴────────────────┐
       │ echo stop >&3                  │
       │   op_lock                      │
       │   读 state=RUNNING power=1     │
       │   rproc_ff5_shutdown_owned()   │  ← 会话身份，admit_owner 放行
       │     → 借走 loader 的票          │
       │     → power=0, ADSP OFFLINE    │
       └───────────────┬────────────────┘
                       │
       ┌───────────────┴────────────────┐
       │ echo start >&3                 │
       │   rproc_ff5_boot_owned()       │  ← 还票
       │     → power=1, ADSP RUNNING    │
       └───────────────┬────────────────┘
                       │
       close(fd)        ← END（释放门控）

     会话期间：loader / sysfs / cdev 的 boot/shutdown 全被 -EBUSY 拒绝
```

#### 八、边界（没做什么）

1. **不替换固件**——只做同固件停启，固件路径始终 `adsp.mdt`。
2. **没做故障注入**——错误固件/认证失败/超时/remove 都没测。
3. **PAS 失败仍会 panic**（原样保留，和现有 loader ssr 路径一致）。
4. 已知不覆盖：
    - `cdev_put_on_release` 会调 shutdown 的路径。
    - msm-kernel 里 PAS 驱动自己的 DTB 名称设置不经过 core 门控。
5. 短采样不证明音频播放、测温准确性、长时间稳定性、DSP 内存无泄漏。
6. `reload=0` 是固定诊断字段，不能据此说实现了版本切换。

> 一句话总结：  
> patch 04 是"在线更新"路上真正的里程碑：之前几步都是"观测/占位"，这一步第一次真正把 ADSP 停下来、再用同一份固件启起来，而且全程不重启 AP（`boot_id` 不变），还验证了 GLINK/rpmsg/audio/sensor 子系统能自动重连。它用"借票/还票"避免改 loader，用 owner 机制让会话自己通过门控，用 trylock + 锁顺序避开 ABBA 死锁。

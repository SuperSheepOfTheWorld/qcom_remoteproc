### patch 03：用 fd 绑定更新会话，真正占住门控

> patch 01 建好了"闸门"（但只能自检，没人能真正锁上）；patch 03 给了你一把"钥匙"——打开 `/dev/ff5_adsp_update` 就是锁门（占住 ADSP），关闭就是开门。

#### 一、它到底做了什么（一句话）

新增一个字符设备 `/dev/ff5_adsp_update`，用 fd 绑定一个"更新会话"：

```
  open("/dev/ff5_adsp_update")  =  BEGIN（占住 ADSP，插门控标记）
  close(fd)                     =  END  （释放门控）

  会话期间：core 的 boot / shutdown / detach / set_firmware / trigger_recovery
           全部返回 -EBUSY（来源包括 loader、remoteproc sysfs/cdev、PM 等）
```

它不停止/不启动 ADSP、不碰硬件，只是"占住"，为后续真正的受控更新（第 05/06 步）铺路。

#### 二、为什么还需要这一步

回顾前两步：

| 步骤 | 做了什么 | 还差什么 |
|---|---|---|
| 01 | 5 个入口加 `admit_locked()` 准入检查 + `ff5_update_gate_probe` 自检 | 门控只能"自检"，没有真正的持有者 |
| 02a/02b | vote 账本 + 修 audio loader 的票 | 知道"只有 1 张票"，但没法把它锁住 |
| 03（本步） | fd 绑定会话，真正占住门控 | 还没有 STOP/SELECT/START |

打个比方：

- ADSP = 一间会议室
- patch 01 = 装了门禁系统（但只能"测试门禁灵不灵"，不能真锁门）
- patch 02 = 装了账本（知道现在只有 1 个人在会议室）
- patch 03 = 发了门禁卡（`/dev/ff5_adsp_update`）：刷卡进 = 占用会议室，离开 = 释放。占用期间，别人想进来、想改会议室配置（boot/shutdown/set_firmware/recovery）全被拒。

#### 三、三个文件改了什么

##### 1. remoteproc_ff5_probe.c（主体，+160 行左右）

###### 新增结构体

```c
  struct ff5_update_dev {
      struct miscdevice misc;    // 字符设备
      struct kref ref;           // 引用计数（注册 + 每个打开的 fd 各一份）
      struct rproc *rproc;       // 对应哪个 ADSP
      bool removed;              // 是否正在注销（保护在 ff5_update_mutex 下）
  };
  static DEFINE_MUTEX(ff5_update_mutex);
  static struct ff5_update_dev *ff5_update_dev;
```

###### 新增 /dev/ff5_adsp_update

```c
  ud->misc.minor = MISC_DYNAMIC_MINOR;
  ud->misc.name  = "ff5_adsp_update";
  ud->misc.fops  = &ff5_update_fops;
  ud->misc.mode  = 0600;          // root 才能读写
  misc_register(&ud->misc);
```

###### ff5_update_open() —— BEGIN（关键！）

```c
  static int ff5_update_open(struct inode *inode, struct file *file)
  {
      if (!capable(CAP_SYS_ADMIN))     // 要求 root
          return -EPERM;

      mutex_lock(&ff5_update_mutex);
      ...
      mutex_lock_interruptible(&rproc->lock);
      state = rproc->state;
      power = atomic_read(&rproc->power);

      /* ★ 只有两种"干净"状态才允许开会话 */
      if ((state == RPROC_RUNNING && power == 1) ||   // ADSP 在跑，只有 loader 一张票
          (state == RPROC_OFFLINE && power == 0))      // ADSP 关着，没人投票
          ret = xa_insert(&ff5_probe_gates, rproc->index, ud, GFP_KERNEL);  // ★ 插门控
      else
          ret = -EBUSY;                                // 状态不干净，拒绝
      mutex_unlock(&rproc->lock);

      if (ret) goto out;
      get_device(&rproc->dev);   // ★ 持有设备引用
      kref_get(&ud->ref);        // ★ 持有 kref
      file->private_data = ud;
  out:
      mutex_unlock(&ff5_update_mutex);
      dev_info(..., "ff5 update session begin: state=%u power=%d ret=%d\n", ...);
      return ret;
  }
```

`xa_insert` 这一行就是"锁门"：往 patch 01 的门控 xarray 里放一个 marker。之后 core 的 `rproc_ff5_admit_locked()` 一查 xarray 发现有 marker，就返回 `-EBUSY`，5 个入口全部拒绝。
[XArray是什么](../remoteproc架构/基础知识补充/linux_kernel-XArray.md)
###### ff5_update_release() —— END

```c
  static int ff5_update_release(struct inode *inode, struct file *file)
  {
      struct ff5_update_dev *ud = file->private_data;
      struct rproc *rproc = ud->rproc;

      mutex_lock(&ff5_update_mutex);
      if (!ud->removed) {
          mutex_lock(&rproc->lock);
          ff5_update_gate_drop_locked(ud);   // ★ 删掉门控 marker（开门）
          mutex_unlock(&rproc->lock);
      }
      mutex_unlock(&ff5_update_mutex);
      dev_info(..., "ff5 update session end\n");
      put_device(&rproc->dev);
      kref_put(&ud->ref, ff5_update_dev_free);
      return 0;
  }
```

##### 2. remoteproc_sysfs.c —— 补上 recovery 标志的门控

###### 修复前（patch 01 的漏洞）

```c
  if (sysfs_streq(buf, "enabled")) {
      mutex_lock(&rproc->lock);
      rproc->recovery_disabled = false;    // ← 直接改标志，没门控！
      ...
  }
```

###### 修复后

```c
  if (sysfs_streq(buf, "enabled")) {
      mutex_lock(&rproc->lock);
      ret = rproc_ff5_admit_locked(rproc);   // ★ 先过门控
      if (!ret)
          rproc->recovery_disabled = false;
      mutex_unlock(&rproc->lock);
      if (ret)
          return ret;                        // 会话期间拒绝
      rproc_trigger_recovery(rproc);
  }
```

为什么要补这个：patch 01 只拦住了"触发 recovery"（`rproc_trigger_recovery`），但没拦住"改 recovery 标志"这一步。会话期间如果有人写 `recovery=disabled`，虽然 trigger 被拦了，但标志被改了，等会话结束就会自动触发恢复——这是个漏洞。这一步补上了。

##### 3. remoteproc_debugfs.c —— 同样的修复

debugfs 的 `recovery_write` 也一样加了门控（`enabled`/`disabled` 两个分支）。

#### 四、生命周期与锁（这段很关键）

##### 锁顺序（单向，不死锁）

```
  misc_mtx（misc_open 持有） → ff5_update_mutex → rproc->lock
```

没有反方向获取，所以不会死锁。

##### remove 的顺序（为什么这么排）

```c
  static void ff5_update_dev_remove(struct rproc *rproc)
  {
      // 1. 先从全局指针摘掉
      mutex_lock(&ff5_update_mutex);
      ud = ff5_update_dev; ff5_update_dev = NULL;
      mutex_unlock(&ff5_update_mutex);

      // 2. 注销 misc 设备（保证没有新的 open 在进来）
      misc_deregister(&ud->misc);

      // 3. 标记 removed + 去掉门控
      mutex_lock(&ff5_update_mutex);
      ud->removed = true;
      mutex_lock(&rproc->lock);
      ff5_update_gate_drop_locked(ud);   // ★ 去掉门控！
      mutex_unlock(&rproc->lock);
      mutex_unlock(&ff5_update_mutex);
      kref_put(&ud->ref, ff5_update_dev_free);
  }
```

两个关键点：

1. `misc_deregister` 保证没有新的 open：因为 `misc_open` 是在 `misc_mtx` 下调用我们的 open 的，注销返回后不会再有 open 在进行。
2. 主动去掉门控（`ff5_update_gate_drop_locked`）：因为 `rproc_del` 后面自己会调 `rproc_shutdown`，如果门控还在，会把自己拦住！所以 remove 时必须先拆门控，保证自己的 shutdown 能过。

##### fd 还开着时怎么办

- `get_device(&rproc->dev)` + `kref_get` 保证：只要 fd 还开着，`ff5_update_dev` 和 `rproc` 都不会被释放。
- release 时如果 `removed=true`（设备已注销），只释放引用，不再碰门控。

#### 五、验收数据说明什么

| 测试 | 结果 | 说明 |
|---|---|---|
| 基线 | `state=2 power=1 gate=0` | ADSP 运行中，1 张票，门控没锁 |
| open | `open=0, gate 变 1, power 仍 1` | 会话打开成功，门控锁上，但没改变 ADSP 运行状态 |
| 会话内 gate_probe | 返回 busy（`probe=1`） | 门控生效，自检也被拒 |
| 会话内写 recovery=disabled | 失败（`recovery=1`） | 新加的 recovery 门控生效 |
| 第二次 open | 失败（`second=1, -16`） | 不能重复开会话（`xa_insert` 失败） |
| close 后 | `gate=0`，自检恢复 `pass=1` | 会话结束，门控释放 |
| 进程退出 | `gate=0`，日志有 end | fd 关闭自动触发 release（内核保证） |
| 账本/loader | 与基线一致（`power=1 net=1 balanced=1`） | 会话期间没有触发 loader，票没变 |

最重要的两条：

- `gate` 从 0→1→0：门控真的能锁能放。
- `power` 始终 1：会话不改变 ADSP 的运行状态，只是"占住"。

#### 六、边界（没做什么，别过度宣称）

提交说明里明确写了，我同意：

1. 不包含 STOP/SELECT/START——会话只是"占住"，不更新固件。
2. 没测试 SIGKILL、模块 remove、其他生命周期入口、SSR、实际固件更新——这些路径要等第 05/06 步。
3. 已知不覆盖：
    - cdev 的 `cdev_put_on_release` 会调 shutdown，被拦后那票会留着。
    - msm-kernel 里 PAS 驱动自己的 DTB 名称设置不经过 core 门控（留到第 06 步）。

```
                      用户态
                        │
          open("/dev/ff5_adsp_update")   ← BEGIN
                        │
                        ▼
          ┌─────────────────────────────┐
          │ ff5_update_open()            │
          │  检查 state==RUNNING&&power==1│
          │   或 state==OFFLINE&&power==0 │
          │  xa_insert(marker)  ← 锁门    │
          │  get_device + kref_get        │

                        │
                        ▼  会话期间
          ┌─────────────────────────────────────────┐
          │ core 的 5 个入口全部 -EBUSY：             │
          │   rproc_boot / rproc_shutdown            │
          │   rproc_detach / rproc_set_firmware      │
          │   rproc_trigger_recovery                 │
          │ + sysfs/debugfs 的 recovery 写            │

                        │
          close(fd)     ← END
                        │
                        ▼
          ff5_update_release() → xa_erase(marker) → 开门
```

> patch 03 把"门控"从"只能自检"变成"真正可用"：用 `/dev/ff5_adsp_update` 的 open/close 绑定一个更新会话，会话期间独占 ADSP 的生命周期控制权（其他所有 boot/shutdown/换固件/恢复全部 `-EBUSY`）。它是"受控在线更新"的外壳——占住 ADSP，等第 05/06 步再在里面真正做 STOP/SELECT/START。
